# 云端部署和维护手册

状态：本地经营与账号恢复流程已实现并通过隔离测试。尚未配置真实云账号、域名和 SMTP 投递，未实际对外发布；下述云端验收完成后再邀请真实商户。

## 环境边界

- 汇报版 `D:\云迹科技` 与商业版 `D:\云迹科技-商业化` 完全独立。只在后者运行下述命令。
- 开发前端 5174，API 4100；Windows 启动器只管理本目录的两个进程，不停止其他端口进程。
- 本机 `.local/database` 是独立 PGlite 数据库；正式部署要求 PostgreSQL，不能复制浏览器 localStorage 当作数据库。
- 经营 JSON 备份只有单个空间的业务记录，不含账号、密码、会话、认证令牌或配置，不能代替整库备份。
- 默认经营日期、周/月/年范围及审计时间展示统一按北京时间（`Asia/Shanghai`）；服务器和浏览器宿主时区不改变经营日期。

## 部署方式

1. 检出 `feat/commercial-pilot`，安装 Node 24、pnpm 11.25.0；运行 `pnpm install --frozen-lockfile`、`pnpm check`、`pnpm test:e2e` 和 `pnpm test:auth:e2e`。浏览器测试使用隔离数据库与内存 fakeMailer，不向真实邮箱发信。
2. 新建专用 PostgreSQL 数据库和账号，限制网络访问范围。应用启动执行增量迁移，当前账号需要本库建表权限；生产权限拆分应在上线复核时完成。
3. 构建仓库 Dockerfile，或安装依赖、`pnpm build` 后运行 `pnpm start`。不得将 `.env`、数据库目录和备份打进镜像。
4. 通过云平台密钥配置下表变量，不提交 Git。

| 变量 | 说明 |
| --- | --- |
| `NODE_ENV` | `production`。 |
| `DATABASE_URL` | 专用 PostgreSQL 连接串，按供应商要求配置 TLS。 |
| `APP_ORIGIN` | 唯一正式 HTTPS 来源，如 `https://app.example.com`，末尾不加 `/`；邮件链接也固定从这里生成。 |
| `INVITE_CODE` | 至少 16 字符的随机邀请码，只交给受邀试用者。 |
| `SMTP_HOST` / `SMTP_PORT` | 邮件服务地址与端口。常见为 465 或 587。 |
| `SMTP_USER` / `SMTP_PASSWORD` | 邮件服务凭据，仅保存在服务端密钥配置。 |
| `SMTP_FROM` | 邮件服务允许使用的发件地址。 |
| `SMTP_SECURE` | 465 使用 `true`（直接 TLS）；587 使用 `false` 并强制 STARTTLS。不得关闭证书校验。 |
| `HOST` / `PORT` | 容器或反向代理环境使用 `0.0.0.0`；端口默认 `4100`。 |
| `TRUST_PROXY` | 仅应用确实位于一个可信代理后时设 `1`，且不能直接暴露应用端口。 |
| `REQUIRE_VERIFIED_EMAIL` | 开发环境可设 `true` 演练验证门槛，此时也必须配置邮件。生产始终强制验证，不能用此变量关闭。 |

5. 由云平台或反向代理提供 HTTPS。前端静态文件与 `/api` 保持同域；生产服务提供 `dist` 静态文件。
6. 配置 `/api/health` 存活检查、错误日志、费用告警和数据库备份，确定实际接收告警与处理故障的人。

生产缺少 HTTPS 来源、邀请码、PostgreSQL 或完整 SMTP 配置会拒绝启动。配置检查通过不证明 SMTP 连通、发信身份正确或邮件已经到达；这些必须在真实服务上逐项验收。本机开发 `.env` 不应直接复制为生产配置。

## 邮件与账号维护

### 本地无 SMTP

公开 `GET /api/auth/capabilities` 返回 `emailEnabled=false`。默认仍允许原有注册、登录和业务流程；邮件申请返回受控的 `EMAIL_NOT_CONFIGURED`，不排队、不生成假邮件。启用强制验证但没有邮件服务时拒绝启动，避免用户无法开通空间。

### 验证与找回

- 生产未验证账号只能使用必要的账号操作；服务器拒绝其经营数据接口，前端显示验证引导。
- 注册成功即创建账号和空间。`emailDelivery=queued` 只代表发信任务已接受；`unavailable` 表示账号已创建但未排队，应稍后重发；`disabled` 表示邮件未配置。
- 验证默认 24 小时、重置默认 30 分钟；令牌单次使用，数据库存散列，不存原文。打开链接不消费令牌，必须明确点击确认或提交新密码。
- 密码恢复撤销目标账号全部旧会话及剩余相关令牌，要求正常重新登录，不自动登录目标账号。恢复响应不发送 `Set-Cookie`，避免晚到响应删掉用户期间新登录的账号 cookie；前端有对应会话世代保护。
- 已登录修改密码保留当前会话，撤销其他会话和未消费令牌。旧链接失效后应重新申请，不通过直接改库绕过凭据版本。

### 投递失败和重发

邮件队列有容量、并发和发送超时限制，保存在进程内，**不具备持久投递保证**。HTTP 202、queued 和“申请已受理”均不能当作送达回执。

1. 未收到邮件时先核对邮箱、收件箱和垃圾邮件，再查看服务端受控投递状态与 SMTP 服务商状态。
2. 服务重启、队列忙或发送失败后，等待冷却期再重新申请。进程中未完成的任务不保证自动补发；不得通过重复注册或重建数据库恢复发信。
3. 已失败的本次令牌会失效；其他仍有效的链接不会仅因一次发送失败被全部撤销。使用有效链接，或等待后重新申请。
4. 找回入口对不存在的账号和邮箱冷却期使用相同公开响应，客服不能把通用“已受理”解释为账号存在或邮件已到达。
5. 重置成功后的安全通知也可能投递失败；通知失败不会回滚已完成的密码恢复。

上线时验证发件地址和域名配置、TLS、正常收件、垃圾箱情况及错误监控。SMTP debug/logger 关闭；日志不得包含令牌、完整恢复链接、邮件正文、密码或 SMTP 凭据。当前内存队列需要在更高可用性要求出现时升级为持久队列。

## 上线验收

- 两台设备验证同账号数据，两个账号验证隔离；检查 HTTPS、安全 Cookie 和代理后的登录限流。
- 用测试数据走客户 → 订单 → 分次收款 → 退款 → 报表，以及商品期初 → 出库 → 预警；在其他时区浏览器确认默认经营日期仍为北京时间。
- 真实 SMTP 下完成注册验证、重发、忘记密码、过期/已消费链接、重置后旧会话失效，以及失败后的重新申请。
- 使用专用 PostgreSQL 测试库演练增量迁移，确认既有账号与全部经营数据保留，未验证账号不能绕过前端读取业务接口。
- 定时备份、恢复、版本回退和告警都实际演练。当前邀请码只支持受邀试用，完整邀请管理仍待扩展，不开放无限制注册。

## 备份与恢复

1. 在数据库服务商启用自动备份及合适的时间点恢复，明确可接受的数据丢失窗口和恢复时间。
2. 使用官方 `pg_dump --format=custom` 制作独立备份。凭据放服务商密钥或受保护的 PostgreSQL service/密码文件，不写进命令历史；备份加密、限制访问并设置保留周期。
3. 使用 `pg_restore --exit-on-error --no-owner` 恢复到全新的测试空库，核对账号、空间、客户、订单、资金与库存流水、审计，以及收款净额和库存余额。
4. 邮件迁移后，恢复检查必须包括 `users` 的密码散列、验证状态与凭据版本，及**非空** `auth_tokens`、`auth_request_limits` 的全部业务字段；只比较空表数量不够。
5. 真正灾难恢复可能恢复旧会话和旧令牌。切换生产前明确撤销恢复库内旧会话/未消费令牌的方案，并让用户重新登录或申请；不要让旧备份重新激活已作废凭据。
6. 恢复演练不覆盖运行中的数据库。通过演练后，发生故障时才按确认的恢复流程切换连接。JSON 备份仍只用于恢复到新的空经营空间。

先在受保护的 PostgreSQL service 配置定义 `yunji_source` 和 `yunji_restore_empty`，后者必须指向刚建的独立空库，再执行：

```bash
pg_dump --dbname="service=yunji_source" --format=custom --no-owner --file="yunji-backup.dump"
pg_restore --dbname="service=yunji_restore_empty" --exit-on-error --no-owner "yunji-backup.dump"
```

`--format=custom` 归档用于 `pg_restore`，默认纯 SQL 导出不适用于此命令；客户端主版本应与源服务器兼容。本例不创建数据库，也不自动切换生产连接。
